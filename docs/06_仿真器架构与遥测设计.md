# NN_Car 仿真器架构与遥测设计

## 目标与边界

Godot 是可视化与交互客户端；C host simulation 是控制、传感器、编码器、电机与车辆状态的唯一真值。实时模式不得在 GDScript 中复制控制器或 plant。回放模式继续使用 C 生成的 CSV，以便复现、审查和离线比较。

车辆模型目前仍是未校准的仿真模型（`verified=false`）；实时只表示 wall-clock paced execution，不代表实时硬件或实车验证。

## 参考架构

- Webots 的外置 controller 将仿真器与控制进程分离，并通过同步 step 保持控制时序。
- CARLA 的 synchronous mode 由客户端 tick 推进固定步长，使状态和传感器帧对应。
- Gazebo 将 backend simulation server 与 GUI frontend 分开，以 transport 交换状态和命令。

本项目采用这些做法中最小、可复现的一部分：C 仿真服务和 Godot viewer 分进程；本机 loopback TCP；一次 `STEP` 请求只推进一个 C line-control 周期。这里先不用分布式消息总线、ROS 或 Godot 自己的物理引擎。

## 进程与时序

```text
Godot Viewer (Windows GUI, ~60 Hz render)
    ├── 3D vehicle / track / camera / HUD
    ├── synchronized telemetry dashboard
    └── TCP client: RESET / MAPDATA / STEP / CLOSE
             │ 127.0.0.1, newline-delimited JSON
             ▼
nncar_live (WSL/Linux C process)
    ├── fixed C line stack and sensor model
    ├── one STEP = line_dt (currently 10 ms)
    ├── five internal motor/plant steps (currently 2 ms each)
    └── telemetry snapshot (no GUI/render dependency)

Headless experiments are orchestrated separately by `tools/python/simctl.py`: a versioned
scenario plan runs one or more deterministic C batch simulations, validates each CSV and
manifest, computes run metrics, and archives the plan and outputs. Godot can then inspect
any individual CSV; it is not required to execute or compare an experiment.
```

Godot's render rate does not set the plant timestep. The client uses an accumulator and requests complete C steps without skipping accumulated control ticks; each request advances a fixed interval. The viewer currently renders the latest returned state (it does not interpolate between snapshots). Pausing means sending no more `STEP` requests. Reset recreates the deterministic C session from its scenario seed.

The socket binds to loopback only. This also allows the current Windows Godot executable to connect to the Linux C process under WSL without attempting to launch a Linux ELF from Windows.

## Wire protocol (v1)

Control requests are newline-terminated ASCII commands; each response is one UTF-8 JSON object on a line. `MAPDATA <byte_count>` is followed by exactly that many UTF-8 JSON bytes and a newline, so the viewer and C service do not need a shared filesystem. `CTRL pid|mlp|int8` switches the C LineFollower and resets the run; its reset response and subsequent state snapshots identify the active controller.

```text
client: RESET 23 0.8 0 0 0.08 3.0 60 [12.0]
server: {"event":"reset","t_us":0,"controller":"pid"}
client: CTRL mlp
server: {"event":"reset","t_us":0,"controller":"mlp"}
client: MAPDATA <byte_count> + newline
        <exactly byte_count UTF-8 JSON bytes> + newline
server: {"event":"ready","map":{"name":"oval",...}}
client: STEP
server: {"event":"state","t_us":8000,"x":...,"y":...,"theta":...,
         "v_target":...,"wheel_v_l":...,"wheel_v_r":...,"pwm_l":...,"pwm_r":...}
client: CLOSE
server: {"event":"closed"}
```

`RESET` with no body restores the server's configured scenario. The parameter form accepts seed, speed, start offset, heading, track amplitude, wavelength, duration, and an optional rail voltage; the optional last field preserves compatibility with older clients. `CTRL` accepts PID, the trained FP32 MLP, or the trained int8 MLP; unsupported or unavailable models are rejected without changing the active controller. Its acknowledgment reports the controller actually applied to the C stack. `MAPDATA` validates and replaces the active map, resets the C session, and returns a fresh `ready` snapshot. Invalid maps leave the previous map in place. Invalid commands receive an error response; a disconnected viewer does not corrupt the C session.

## Telemetry dashboard

The workbench is split into a pinned left rail and a compact bottom transport/timeline
dock. Waveforms are shown only in the detached **Charts** window. The rail keeps run
identity, scenario/seed, the primary tracking errors, a magnified gray-sensor array and a
safety block visible while the 3D view is inspected. The detached window contains a
six-band strip chart that shares one time cursor with the car replay and the bottom timeline.
It shows:

1. lateral / cross-track error (mm), computed from pose and reference track, with the
   physical line-width band;
2. heading error (degrees), relative to the reference track tangent;
3. target and measured forward speed (m/s);
4. target yaw rate and pose-derived yaw rate (rad/s);
5. left and right applied PWM;
6. line confidence and valid sensor ratio.

Value scales are computed from the run envelope and expand monotonically, so the traces do
not jitter while data arrives. Hovering a chart switches its readouts to the hovered sample;
clicking or dragging seeks the run cursor. The wheel zooms the time axis and middle-drag
pans; **Fit** restores the full run. Fault and recovery spans tint the chart background and
the timeline, and the safety block lists active fault bits by name (with latched and output
stop states).

The detached **Charts** window is the only waveform view; zoom and pan apply there, while
the bottom timeline remains available in the main window. Live and replay data share the
same telemetry row shape; recorded live sessions can be reopened as ordinary CSV logs.

## Modes

- **Live / lockstep**: C advances one fixed control step per request. Godot renders the latest state and can save a run.
- **Replay**: loads a complete C-generated or recorded CSV; supports pause, speed changes, scrubbing, and synchronized plots.
- **Batch experiment**: `simctl` runs scenario/seed matrices headlessly and stores per-run logs plus metrics.
- **Analysis**: inspect individual runs in Godot or compare their structured summaries outside the viewer.

The existing batch `nncar_sim` and its CTest/golden checks remain unchanged at the command/API level; batch execution is implemented on top of the same incremental C session used by `nncar_live`.
